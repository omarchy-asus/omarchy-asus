# omarchy + omarchy-settings 4.0.5-1.1 (EXPERIMENTAL)

**Base:** Omarchy's `omarchy` and `omarchy-settings` 4.0.5-1 recipes (omacom/omarchy-pkgs
`0126fa4` "Release omarchy 4.0.5", source omacom/omarchy `v4.0.5` = `94a8fbc2`). Both
packages build from the same source tree, so `recipes/omarchy` and `recipes/omarchy-settings`
carry the **same** patch list, in the same order (their DELTA files must stay in lockstep).
`omarchy` pins `omarchy-settings=$pkgver`. Only pkgver is pinned, so a stock and a patched
half of the same pkgver still install together.

**Why we patch stock Omarchy:** the maintainer's rule is to carry every fix in this repo
today and get each one upstream in parallel. Several fixes edit Omarchy's own scripts
(`omarchy-powerprofiles-set`, `omarchy-hw-webcam`, the shell QML), and no hook can reach
them. Carrying the fork's migrations here also means the fixes that live in user config
or `/etc` arrive with a regular `omarchy update`.

**Our changes to Omarchy's PKGBUILDs:** `pkgrel=1.1`, plus the patches below added to
`source`/`sha256sums` and applied at the end of `prepare()` (`patch -d "$srcdir/omarchy"`).
All of it is generated by `bin/rebase-recipe` from `DELTA`.

**Patches:** the omarchy-asus fork's fixes (written against `quattro`), backported onto
v4.0.5 as fork branch `asus/v4-0-5`, one commit each. Commit messages name the fork
commit (`Backport-of:`) and any adaptation.

**PKGBUILD change (omarchy-settings only):** `pkgbuild-source-monitor-unit.diff` installs the
charger-swap monitor user unit (from 0002) in `/usr/lib/systemd/user`. omarchy-settings installs
user units from an explicit list, so without it first-run and migration `1792174852` would
enable a unit systemd can't find. Same change as fork pkgs branch `omarchy-settings-source-monitor`.

**Left out on purpose:** the GA605KM touchpad wake, `HibernateMode=shutdown` and the
nvidia-powerd start limit (shipped by `omarchy-asus-g16` under `/usr/lib`, no `/etc`
path in common), and the Win-lock helper (`asus-rog-nkey-winlock`).

**Migrations run on `omarchy update`.** Each one runs once per user. On a machine where the
same fix was made by hand:
- `1787683023` (initramfs): on a hybrid machine it deletes `/etc/mkinitcpio.conf.d/nvidia.conf`
  and rebuilds the initramfs, whatever that file contains now (a hand-edited copy is lost;
  it restores the file if the rebuild fails).
- `1789747667` (rtkit): if rtkit is already installed, it still restarts the portal and
  PipeWire once (a short audio drop).
- `1792123636` (video pins): it only skips mpv options set at the top level of
  `~/.config/mpv/mpv.conf`; a `hwdec`/`vaapi-device` inside a `[profile]` or a `conf.d`
  file gets a second pin. Chromium is skipped when `--render-node-override` is present.
- The others check before acting or only print a message.

So **don't publish these until the test laptop's hand-made equivalents are switched off.**

**Tests:** on the backport branch, every test file for a changed script passes. The full
`test/shell` suite has no failure that plain v4.0.5 doesn't also have (those come from
the sandbox: no omarchy-pkgs checkout, no network). shellcheck is clean apart from
SC2119/SC2120 notes in the fork's `hybrid-video-decode.sh`. Not yet installed on hardware.

**Known limit:** with `OMARCHY_SRC=<tree>` (a local source build), `source=()` is empty, so
the patches aren't downloaded and `prepare()` fails. Build from a tree that already has
the fixes with Omarchy's own recipe instead.

**Rebase when Omarchy moves:** `bin/auto-update` does it from `DELTA`
(`bin/rebase-recipe omarchy --version <ver> --out <dir> --verify` by hand, then the same for
`omarchy-settings`). If a patch stops applying, regenerate it from `asus/v4-0-<z>`
rebased onto the new tag. Drop a patch once a release we build from contains it.
