# omarchy + omarchy-settings 4.5.0rc1-1.108 (EXPERIMENTAL, release candidate)

**Base:** Omarchy's `omarchy` and `omarchy-settings` 4.5.0rc1-1 recipes (omacom/omarchy-pkgs
`bed2ea5` "Release omarchy 4.5.0rc1" on its `rc` branch, source omacom/omarchy `v4.5.0-rc1` =
`03ff1eff`). A release candidate, on the RC channel only (branch `next/omarchy-4.5`, release
`rc-x86_64`): the Quattro channel (`main`, release `x86_64`) keeps the 4.0.6 recipes until Omarchy's
stable channel moves. Both
packages build from the same source tree, so `recipes/omarchy` and `recipes/omarchy-settings`
carry the **same** patch list, in the same order (their DELTA files must stay in lockstep).

`omarchy` pins `omarchy-settings=$pkgver-$pkgrel` (`pkgbuild-pin-settings-release.diff`), so a
patched omarchy cannot install next to stock's omarchy-settings of the same pkgver. The two
recipes form a release cohort in `build/cohorts.conf`: `bin/publish` refuses to publish one
member without the other at the same version, `bin/unpublish` withdraws both, and
`bin/auto-update` holds a built member back until its partner is built at the same version (#83).

**Why we patch stock Omarchy:** the maintainer's rule is to carry every fix in this repo
today and get each one upstream in parallel. Several fixes edit Omarchy's own scripts
(`omarchy-powerprofiles-set`, `omarchy-hw-webcam`, the shell QML), and no hook can reach
them. Carrying the fork's migrations here also means the fixes that live in user config
or `/etc` arrive with a regular `omarchy update`.

**Our changes to Omarchy's PKGBUILDs:** `pkgrel=1.108` (1.101: the 1.2 build, 0024 refreshed to omacom/omarchy#15912, renumbered into the RC channel's pkgrel range; 1.102: 0016 follows the IPN bus instead of polling; 1.103: 0007 drops the session-wide NVIDIA GLX on a non-VGA iGPU; 1.104: general-0001; 1.105: 0025; 1.106: general-0002; 1.107: 0026 keeps the RTX asleep while apps start; 1.108: general-0003), the same in both recipes because
omarchy's pin names it, the `(omarchy-asus build)` label in `pkgdesc`, plus the patches below
added to `source`/`sha256sums` and applied at the end of `prepare()`
(`patch -d "$srcdir/omarchy"`). All of it is generated by `bin/rebase-recipe` from `DELTA` (a
rebase sets upstream's pkgrel + `.1` in both recipes, so they stay in step; a later change to
the package content without a new upstream release bumps the `.1` by hand in both).

**PKGBUILD change (omarchy only):** `pkgbuild-pin-settings-release.diff` adds
`depends+=("omarchy-settings=${pkgver}-${pkgrel}")` in `package()`, so only the patched
omarchy-settings from the same release satisfies the package, never stock's same-pkgver build
(#83). Upstream's `omarchy-settings=${pkgver}` in the global `depends=()` stays: that is what
`makepkg -s` installs in the clean chroot and in CI, where only stock omarchy-settings exists.

**Native OpenGL games need PRIME render offload on the G16 (0007, #264).** Where the iGPU is a non-VGA
display controller (AMD Krackan on the G16), stock Omarchy reads NVIDIA as the display GPU and
sets `__GLX_VENDOR_LIBRARY_NAME=nvidia` for the whole session, so every GLX app (the Steam
client, `steamwebhelper`) kept the RTX awake. 0007 leaves the GLX vendor unset there, as it
does `LIBVA_DRIVER_NAME`, so plain apps stay on the iGPU and the RTX can suspend. The trade-off:
Proton/DXVK games are unaffected (DXVK picks the discrete GPU itself), but a native OpenGL game
now runs on the iGPU unless its launch options ask for the RTX:
`__NV_PRIME_RENDER_OFFLOAD=1 __GLX_VENDOR_LIBRARY_NAME=nvidia %command%` in Steam, or
`prime-run %command%` where `nvidia-prime` is installed (Omarchy doesn't install it). Migration
`1792775464` asks for a reboot while the running session still carries the old variable.

**Games and the RTX's sleep at app startup (0026, #218).** nvidia-open resumes a runtime-suspended
GPU for every call into the driver, even one that only asks which GPUs exist, so any app that
lists Vulkan devices or opens surfaceless or device EGL at startup (GTK, Chromium, Electron)
woke the RTX for about 20 s, whichever GPU it went on to use. The G16 trace on #218 showed
Vulkan enumeration with NVIDIA's ICD present, and surfaceless/device EGL in the stock vendor
order, waking it; Radeon's ICD alone, and Mesa first for surfaceless EGL, kept it asleep (Radeon
first with NVIDIA listed still woke it, hence disabling NVIDIA's ICD rather than reordering).
EGL lists Mesa's vendor alone for the same reason: GLVND asks every listed vendor for its devices,
whatever their order. EGL on the Wayland display never woke it.

The pins are for the desktop only, never for games. Hyprland sets them for what it starts (the
shell, the launcher and dock and their apps, key bindings, terminals); uwsm-app runs an app in its
caller's environment, so those inherit them. Games get every GPU back on each path they start by:
from a terminal (the interactive bash drops the pins), at login (autostart.lua unsets them in the
systemd user environment after exporting the rest, so xdg autostart, Steam's included, has
every GPU), from the launcher or dock as a game entry (`omarchy-launch-desktop-entry`), or through
`omarchy-launch-all-gpus`. Steam itself may then run on the Radeon or wake the RTX at start;
either is fine, its games pick the RTX. What still inherits the pins: a game or game launcher
started by an ordinary desktop app (a file manager opening a game, a browser starting Steam
through a `steam://` link while Steam is closed), a launcher entry that is none of the game kinds
above, and shells other than bash. Those run their games on the Radeon until started one of the
ways above. Native OpenGL games still need PRIME render offload as above.

**PKGBUILD change (omarchy-settings only):** `pkgbuild-source-monitor-unit.diff` installs the
charger-swap monitor user unit (from 0002) in `/usr/lib/systemd/user`. omarchy-settings installs
user units from an explicit list, so without it first-run and migration `1792174852` would
enable a unit systemd can't find. Same change as fork pkgs branch `omarchy-settings-source-monitor`.

**Left out on purpose:** the GA605KM touchpad wake, `HibernateMode=shutdown` and the
nvidia-powerd start limit (shipped by `omarchy-asus-g16` under `/usr/lib`, no `/etc`
path in common), and the Win-lock helper (`asus-rog-nkey-winlock`).

**Migrations run on `omarchy update`.** Each one runs once per user. On a machine where the
same fix was made by hand they leave it alone (patches 0021-0023):
- `1787683023` (initramfs): on a hybrid machine it deletes `/etc/mkinitcpio.conf.d/nvidia.conf`
  and rebuilds the initramfs only when the file is byte for byte what Omarchy's installer
  wrote (`MODULES+=(nvidia nvidia_modeset nvidia_uvm nvidia_drm)`). Any other content is kept,
  with a one-line note, and nothing is rebuilt. No file: nothing to do. A failed rebuild
  still puts the file back.
- `1789747667` (rtkit): restarts the portal and PipeWire (one short audio drop) only when
  this run installed rtkit (`pacman -Q rtkit` before installing), or rtkit was installed
  after this user's running portal or PipeWire started (another user's run). rtkit there
  before the session: nothing restarts.
- `1792123636` (video pins): mpv.conf is left untouched when `hwdec` or `vaapi-device` is
  set anywhere mpv reads it: any `[profile]` of `~/.config/mpv/mpv.conf` or any file pulled
  in with `include=`, nested too (mpv has no `conf.d`; an unreadable include counts as set).
  Omarchy's own lines don't count. Each Chromium-family flags file that already has
  `--render-node-override` is skipped. Pins Omarchy writes sit under a marker comment
  (0020), so only those are ever repinned.
- The others check before acting or only print a message.

Released (the HOLD came off once these migrations were made safe, by the maintainer's goal of
shipping every fix through `omarchy update`). One overlap remains a choice: a machine running its
own power daemon should set Omarchy's `powerprofiles-autoswitch-off` toggle (0003 honours it) or
stop that daemon, so the two don't both switch profiles on plug and unplug.

**Known limit:** with `OMARCHY_SRC=<tree>` (a local source build), `source=()` is empty, so
the patches aren't downloaded and `prepare()` fails. Build from a tree that already has
the fixes with Omarchy's own recipe instead.

**Rebase when Omarchy moves:** `bin/auto-update` does it from `DELTA` for stable releases
(`bin/rebase-recipe omarchy --version <ver> --out <dir> --verify` by hand, then the same for
`omarchy-settings`; it finds a release on omarchy-pkgs' `master`, or a pre-release such as
4.5.0rc1 on `rc`). `bin/check-upstream` follows Omarchy's stable channel, so while these recipes
sit on a release candidate it reports them `upstream-older` and auto-update leaves them to a
human: the rc build is built and published by hand on the RC channel (`bin/build-pkg`,
`bin/publish` and `bin/sync-release` with `--channel rc`; README.md "Release channels"), and
the move to 4.5.0 final is a rebase by hand too. If a patch stops applying, regenerate it from `asus/v4-5-0-rc1` (or the newest
`asus/v<x>-<y>-<z>`) rebased onto the new tag. Drop a patch once a release we build from
contains it.
